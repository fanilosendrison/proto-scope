### Discovery (atomic statement)

The bound provider's repository-governance-state load deadlocks whenever the
governed repository root contains an ignored tree large enough to fill the
`git check-ignore` pipe pair. `repository_state::git::run_git_with_optional_input`
writes the entire untracked-path query to the child's stdin before reading the
child's stdout (`wait_with_output`), while both stdout and stderr are piped.
`git check-ignore --no-index --verbose -z --stdin` echoes four fields per
matching path, so a real Python virtual environment under the repository root
saturates the 64 KiB stdout pipe; the child then stops draining stdin and the
parent blocks forever in `write(2)`.

### Content independence

The same deadlock reproduces on the **unmodified persistent checkout** at the
exact baseline `031941b5…` (2075 ignored files under its `.venv`). It is not
caused by the candidate migration changes and is not repository-content
selective.

### Why this is not an ordinary implementation defect

* The defective code is in Proto-Ring (`crates/proto-ring-engine/src/repository_state/git.rs`).
  Task constraints forbid any Proto-Ring modification.
* The Python provider at the previous pin `dedb01a3…` contains **no**
  `check-ignore` call at all (0 files matched at that commit), so the Rust port
  introduces this capability and its failure mode; there is no preserved
  behaviour to fall back to inside the authorized boundary.
* Turnlock's canonical validation environment places `.venv` inside the
  repository root (`AGENTS.md`; Issue #71 Phase-2 §27 explicitly fixes
  `python3 -m venv .venv` and `.venv/bin/python scripts/check-repository-integrity.py`).
  §28 additionally mandates a fresh task-local venv plus full Repository
  Integrity, and §32 the canonical run.

### Consequence

Every operation that loads repository governance state blocks: 
`repository-governance-state.compose`, `evidence-requirements.registry`, and
`repository-integrity.evaluate`. The affected validator surface is the
compose-based checks (governance authority, governed objects, structured
governance, binding-registry currentness), the Evidence Requirements loading in
formal traceability, and the canonical integrity entry point itself.

Therefore `CLEAN_NATIVE_REPOSITORY_INTEGRITY`, `TURNLOCK_REPOSITORY_INTEGRITY`,
and the §31/§32 qualification cannot be satisfied in the mandated environment.
